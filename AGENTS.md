# Working on this project

Start with `tasks/NEXT_SESSION.md`; read `docs/STATE.md`, the relevant task record, and `docs/AGENT_WORKFLOW.md` before implementation. Consult `docs/PROJECT_PLAN.md` for scope and `docs/BUILD_AND_VALIDATION.md` for acceptance evidence.

- Use regular ASCII hyphens in new prose instead of en dashes or em dashes.
- External contributions are not currently accepted; see CONTRIBUTING.md. Authorized internal agent work and independent review continue unchanged.
- Implementation is underway. Consult docs/BUILD_AND_VALIDATION.md for the implemented command inventory; unimplemented interfaces and scheduling remain proposals, not available capabilities.
- Keep verified observations, hypotheses and implementation decisions distinct. Support gameplay claims with a ROM identity, addresses or traces, a reproducible experiment and the precise tested domain.
- Write native code for human contributors: descriptive names for established concepts, small explicit update functions, documented units/integer semantics, and evidence links for recovered behavior. Keep uncertain meanings provisional; defer speculative mod frameworks. Refactor under frozen differential checks (D-0003).
- Preserve original integer arithmetic, ordering and timing when reconstructing behavior. Do not replace unknown mechanics with plausible inventions while describing the result as accurate.
- Follow [D-0004](docs/decisions/D-0004-model-and-usage-budget.md): keep each task and its children within its starting provider unless the user moves it; use Sol/medium for routine OpenAI coordination and implementation, explicit child models, one active child by default, bounded frontier consultations, and recorded quota guardrails. Preserve independent review; never automatically buy or redeem credits.
- Follow [D-0006](docs/decisions/D-0006-capability-driven-work.md) for M4-12 through M4-16: Astra/medium owns recovery and native implementation directly; coupled producers are internal experiments, not separate acceptance tasks. M4-16 targets playable ZOOM ZOO from native initialization through result and restart; coupled recovery stays inside the task, with no seed-based or headless-only acceptance fallback. The primary must automatically spawn a fresh Sol/medium independent reviewer in an isolated checkout, handle findings and re-review, and integrate without asking the user to launch review. The task-specific M4-12/M4-13/M4-14/M4-15/M4-16 model/budget exceptions in D-0004 override general defaults; preserve the review reserve and explicit reset-authorization boundary.
- Follow [D-0008](docs/decisions/D-0008-static-map-track-breadth-review-tiers.md): read the static code map's listing (once STATIC-CODE-MAP exists) before designing a capture, and cite it as the source of a routine's reading, but a gameplay claim still needs dynamic evidence; classify every task at claim into review tier 1 (arithmetic and state: full D-0006 process), tier 2 (presentation, content, tooling: one independent round) or tier 3 (records and regenerated maps: none), record the tier and reason in the task record, and let a reviewer escalate. Executing the original code inside the product, for any screen, is rejected by the user and is not to be re-proposed.
- Follow [D-0007](docs/decisions/D-0007-advisory-jev-judgments.md) for `project.py judge`: a Jev judgment is an optional check and a recorded artifact, never a gate or gameplay evidence; the key stays in the environment or the ignored `.env`.
- Work only within the assigned task and ownership boundaries. For concurrent work, each worker uses a separate checkout/worktree; the coordinator owns the shared task registry and integration branch.
- Update the handoff with the actual commit, commands, results, unresolved issues and next experiment. A fresh agent must be able to resume without the previous conversation.
- Treat missing prerequisites and skipped tests as such; never report them as passes. Do not weaken or regenerate expected results merely to make a change pass.
- Keep ROMs, extracted game content, save states, credentials and large generated traces out of tracked files. Inspect the staged diff before committing.
- Local state has one home per kind, all in the main checkout: ROM-derived captures and other evidence a record or gate cites live under `local/evidence/<task-worktree>/`; closeouts and gate logs under `artifacts/<task>-integration/`; nothing under `.worktrees/` is evidence, and a gate script's inputs never point into another worktree (the `cd` lines of retained historical scripts, and older records, still name checkouts that no longer exist). When a task is integrated, the closing session moves its captures and closeout there, deletes its build output and any exploration or fuzz output no record cites, pushes or verifies by patch-id every branch it created, removes its worktree and local branches, and lists what it moved and deleted in the task handoff. Verify a duplicate capture identical (`diff -rq`) before deleting the copy; never delete a capture a record cites.
- Local tests, reversible fixes and task-scoped commits may proceed within the user's authorization. For this repository's already-configured public `origin`, normal source-control synchronization is also authorized and required, and **every change reaches `main` through a pull request**: push the task branch, open a pull request with `.github/pull_request_template.md`, and merge it with a merge commit (`gh pr merge --merge`) once its required checks pass on an up-to-date branch and its review tier is satisfied. Opening, updating and merging the project's own pull requests is authorized; pushing to `main` directly is not, and `main`'s ruleset refuses it. Push an accepted milestone tag. After merging, fast-forward the local `main` and verify it equals `origin/main`; if a push or merge fails, record and report the exact failure instead. The user made this repository public and authorized continued ordinary source-control synchronization. These pushes and pull requests expose tracked source and documentation publicly; they do not authorize a release or deployment. This document does not grant authority to create or replace a remote, change repository visibility or settings, force-push/overwrite remote history, publish a release, deploy, spend money or send messages to other people.
- The independent reviewer posts its report as a comment review on the pull request (`gh pr review --comment`), not as a file or `review/*` branch; see "Where the review goes" in `docs/AGENT_WORKFLOW.md`.
- Pull request descriptions are for a human reader: what changed, why (linking the task record with an absolute URL rather than restating it), the key evidence with numbers, the review and what is not covered, in about 30 lines. Plain sentences, no process narration or filler. The description becomes the merge commit message, so bring its Review section up to date before merging.
- The user's stated goal is to see whether agents can carry this project end to end with minimal interaction while following the source-control and review practices above. Make project decisions yourselves (scenario and track choice, capture methods, task ordering, design tradeoffs, estimates, which ready task to dispatch) and record them in the task, decision or state records with their rationale; do not stop to ask. Ask the user only for what an agent cannot obtain or do itself: machine or account access, private inputs such as a ROM or fixture, money, releases or deployment beyond ordinary synchronization to the configured public origin, deleting things the agent did not create, or a choice the user has explicitly reserved. A wrong but recorded and reversible decision is preferred to a session that ends waiting for one.

- An internal research dependency, a task boundary, or a checkpoint is not a user blocker. The coordinator must resolve the prerequisite and continue toward the active user objective without asking the user to choose or resume the next step. Under D-0006, keep coupled prerequisites as experiments within the current task; create a separate task only when ownership, outcome or review size/risk justifies it. Session checkpoints are for reassessment and recovery, not an automatic end to the request. Stop for user intervention only when the dependency actually requires their access, private input, reserved decision, or authority; do not describe unfinished research as requiring them.

Model-specific entry files should point to this document rather than duplicate project policy. Do not introduce model-specific dependencies into the game or evidence formats.
