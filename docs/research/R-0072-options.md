# R-0072 - OPTIONS paths and persistent data

Status: research in progress, 29 September 2026 UTC. This record distinguishes PAL observations from provisional interpretations. The complete native OPTIONS capability is not yet accepted.

## Identity and method

- Original: headerless European PAL ROM, 2,097,152 bytes, SHA-256 `a1105819d48c04d680c8292bbfa9abbce05224f1bc231afd66af43b7e0a1fd4e`.
- Reference: pinned bsnes `7d5aa1e656b9` with patch SHA-256 `a719f5ffe2222dad4c1ab04336633319ad85004f74e32fc14893a058be333885`, Strict serialization, default deterministic options and scripted pad inputs before each numbered frame.
- Reproduce the captures with `python3 tools/project.py coverage capture --manifest local/evidence/options/<name>.json --out local/evidence/options/<name> --frame-image <frame> --task OPTIONS`, using the manifest's frame count and image labels. `local/evidence/options/` in the main checkout retains manifests, captures and `probe.py` for selected work RAM and cartridge RAM snapshots. The original ROM and all derived output stay ignored.
- Static reading before capture design: `local/evidence/static-code-map/static-map/bank-80.lst` at `$80:B626-B66D`. It marks the OPTIONS dispatcher unknown/gap candidate, with five text pointers at `$80:B66E` and a distinct branch table at `$80:B6C2`. This reading guided captures; the behavior below rests on executed coverage and pictures.
- The first `define-player-first` coverage run executed all 1,800 frames but failed its trace-window gate because it requested 96 entries while the gate checks 64. It is not a passing capture. `define-player-first-valid` reran the same pads with 64 entries and all required checks passed. The two runs' frame samples are identical.

## Verified observations

1. The cold `entry-timeline` capture selects OPTIONS at frame 620. The old main-menu text remains in frame 621, the horizontal slide is underway at frames 630 and 650, and the new menu is settled by frame 670. Its five choices are RECORDS, DEFINE PLAYER, RENAME PLAYER, DEFINE LEAGUE, MAIN MENU. All 900 frames before the next scripted divergence in `define-player-first-valid` have identical video, whole work RAM SHA-256 and first 512 work RAM bytes to the earlier COVERAGE-ROADMAP `mode-4` capture. The user's contemporaneous controller use did not affect the headless run.
2. On `define-player-first-valid`, Down at frame 900 and Start at 960 open WHICH ONE, then Start at 1250 selects MIKE. Frame 1350 shows a warning that removal requires SELECT+Y+A. An isolated Y press at 1500 leaves that warning on screen through frame 1700. On `define-player-confirm`, SELECT+Y+A at frame 1600 enters the name editor by frame 1900. The warning's cancel variant stays on the warning through frame 1900.
3. On `rename-player`, two Down presses and Start enter RENAME WHO; Start on MIKE opens the character picker by frame 1300. The picker is still displayed at frame 1450. No cartridge RAM name bytes changed in snapshots at frames 700, 950, 1150, 1300 and 1450. In `rename-letter-up-a`, Up at 1500 and A at 1560 select G and increase the editor length (`$008D`) to 1 without changing SRAM. In `rename-g-finish`, navigation to OK and A at 2000 completes on frame 2001: MIKE's first eight name bytes become `67 ff ff 74 65 76 65 5f`, the checksum at `$77:016C-016D` changes, and the display reads G. The stale tail is an observed ROM behavior, not a normalized name. `rename-g-then-define-player` shows G in the rider picker and warning, then its define-player confirmation clears the name again.
4. On `define-league`, three Down presses and Start show the six league slots, ONE through SIX, each DEFINE ME. Start on ONE produces a warning by frame 1450. `define-league-confirm` presses SELECT+Y+A at 1650 and shows PICK YOUR LEAGUE by frame 1950; `define-league-cancel` presses Y and remains on the warning. A single Start at 2100 on the first rider leaves the rider picker showing `2 MIN` through frame 2700 and changes no further SRAM byte. The selection count and completion path remain to be measured. The native LEAGUE tournament itself is outside this task.
5. The four RECORDS categories have distinct screens on their tested cold paths. `track-records` shows tour medals and three empty time slots at frame 1300. `records-high-scores` shows zeroed win/loss/race/stunt averages at 1300. `player-scores` shows MIKE's zeroed summary at 1300. `group-tables` shows the empty DEFINE ME league table at 1300. These are cold-data observations only; they do not establish navigation across tours, populated records, scoring formulas or persistence.
6. On the cold `rename-player` path, the 352 bytes of cartridge RAM `$77:000C-016B` at frame 700 are byte-identical to the pinned ROM bytes from file offset `0x1800C`, the v27 pack's `front-end.rider-names` source. `define-player-confirm` changes MIKE's four non-underscore name bytes at offsets `0x000C-000F` to underscores at frame 1600, plus checksum bytes `0x016C-016D`; it changes no other SRAM bytes through 2050. Its Y-only control changes no SRAM byte. `define-league-confirm` changes the label at `0x016E-0178`, checksum bytes `0x022E-022F` and mode word byte `0x0742` at frame 1651; its Y-only control changes no SRAM byte through 2050. These claims cover a cold MIKE and first league slot only, not populated data or the whole reset behavior.
7. The native unmodified OPTIONS mode stops at the main-menu choice. An `app-debug` baseline build in `.worktrees/options` passed with the pinned isolated toolchain. No native OPTIONS implementation is yet compared.
8. `define-player-populated-confirm` injects MIKE races 5, wins 3, best time `0x1234`, a medal 1, first record holder 0, and tour level 1 after frame 800. SELECT+Y+A at 1600 resets those fields to the cold values at that frame along with the name and checksum: races/wins 0, best `0xEA5F`, medal 0, record holder `0x10` (SOMEONE), level 0. The cold confirmation alone would not have shown these dependent changes.
9. The first native slice extracts four exact ROM entries for OPTIONS and RECORDS text and arrow columns in proposed pack profile v28 (446 entries). An `app-debug` build passes. `entry-timeline` compares 13/13 pictures equal through frame 670, `records-high-scores` compares 3/3 pictures equal through frame 1050, and the sampled arrow, selection and slide fields agree except the frame-620 pre-slide countdown check in the local comparison script. Five hidden OAM tile bytes at entries 64-68 differ at and after OPTIONS frame 660; these differences are unresolved. Detail views and editing still raise an explicit native error. This is partial implementation evidence, not acceptance.
10. `records-back` presses Y on the RECORDS category menu at frame 1050; it slides back to the OPTIONS menu, with choice zero selected by frame 1090. `records-main` selects category choice four at frame 1210 and returns directly to the main menu by frame 1250. The native slice matches all five and four captured pictures respectively. Both new PAL captures pass their required capture gates.
11. `rename-g-reset-extended` continues the G rename through return to the main menu, the HUNTER code route, its ending and soft reset. At frame 2001, and again after reset at frames 4000, 4100, 4200, 4400 and 4550, the original SRAM name bytes `$77:000C-001B` remain `67 ff ff 74 65 76 65 5f ff ff 5f 5f 5f 5f 5f 5f`; checksum `$77:016C-016D` remains `31 6d`. The capture passes required gates, and frame 4550 shows the reloaded main menu. The original's name checksum is the 16-bit wrapping sum of little-endian words over `$77:000C-016B`: both cold `97 b0` and renamed `31 6d` agree with that calculation. This is one renamed player and one code-route soft reset, not a claim about app relaunch.
12. Native state now owns the 352 name bytes in `OnePlayerRecords`, initialized from exact pack content on cold boot and preserved by its existing soft reset. Menus and results read that state, and the app and laboratory runner pass the state names to race presentation. A full `app-debug` build and `front_end_tests`, `frontend_contract_tests`, `content_pack_tests` pass. The runner's cold name bytes and name checksum match original SRAM at the compared frame. No editor write path exists yet, so persistence after a native rename remains untested.

On `rename-player` through frame 1450, the picker timing, sampled arrow/slide/text/OAM state and four pre-keyboard pictures agree, except the five previously noted hidden OAM tiles; native reaches the keyboard at frame 1293. ## Provisional interpretations and decisions

- The static branch table suggests RECORDS enters `$80:D525`, DEFINE PLAYER `$80:C12A`, RENAME PLAYER `$80:D448`, and DEFINE LEAGUE `$80:9BC4`. The new captures execute each of those ranges, but their precise entry/exit and all subroutines need a regenerated dynamic listing before citing their meanings in code.
- Mutable player names are owned by `OnePlayerRecords`; the immutable pack table initializes them on cold boot. An Astra/medium read-only architecture consultation found direct pack-name consumers in rider selection, NOW PLAYING, local modes, result screens and race HUD, plus a soft-reset path that preserves records alone. The native owner and consumers were updated after the G and reset captures. `front_end_runner --records` now writes the 352 name bytes and their checksum, but still has a partial SRAM projection and cannot prove whole-SRAM equality for this task.
- Next experiment: implement the evidenced league path and compare its exact mutation frames, then test reset and populated records navigation. Implement the record views under exact frame, picture and SRAM comparisons, and preserve unchanged SRAM ranges as a check. The G return's frame-2003 cursor difference and T's partial printer bytes remain open presentation timing checks.
