# R-0072 - OPTIONS paths and persistent data

Status: research in progress, 29 September 2026 UTC. This record distinguishes PAL observations from provisional interpretations. No native OPTIONS behavior is yet claimed equal.

## Identity and method

- Original: headerless European PAL ROM, 2,097,152 bytes, SHA-256 `a1105819d48c04d680c8292bbfa9abbce05224f1bc231afd66af43b7e0a1fd4e`.
- Reference: pinned bsnes `7d5aa1e656b9` with patch SHA-256 `a719f5ffe2222dad4c1ab04336633319ad85004f74e32fc14893a058be333885`, Strict serialization, default deterministic options and scripted pad inputs before each numbered frame.
- Reproduce the captures with `python3 tools/project.py coverage capture --manifest local/evidence/options/<name>.json --out local/evidence/options/<name> --frame-image <frame> --task OPTIONS`, using the manifest's frame count and image labels. `local/evidence/options/` in the main checkout retains manifests, captures and `probe.py` for selected work RAM and cartridge RAM snapshots. The original ROM and all derived output stay ignored.
- Static reading before capture design: `local/evidence/static-code-map/static-map/bank-80.lst` at `$80:B626-B66D`. It marks the OPTIONS dispatcher unknown/gap candidate, with five text pointers at `$80:B66E` and a distinct branch table at `$80:B6C2`. This reading guided captures; the behavior below rests on executed coverage and pictures.
- The first `define-player-first` coverage run executed all 1,800 frames but failed its trace-window gate because it requested 96 entries while the gate checks 64. It is not a passing capture. `define-player-first-valid` reran the same pads with 64 entries and all required checks passed. The two runs' frame samples are identical.

## Verified observations

1. The cold `entry-timeline` capture selects OPTIONS at frame 620. The old main-menu text remains in frame 621, the horizontal slide is underway at frames 630 and 650, and the new menu is settled by frame 670. Its five choices are RECORDS, DEFINE PLAYER, RENAME PLAYER, DEFINE LEAGUE, MAIN MENU. All 900 frames before the next scripted divergence in `define-player-first-valid` have identical video, whole work RAM SHA-256 and first 512 work RAM bytes to the earlier COVERAGE-ROADMAP `mode-4` capture. The user's contemporaneous controller use did not affect the headless run.
2. On `define-player-first-valid`, Down at frame 900 and Start at 960 open WHICH ONE, then Start at 1250 selects MIKE. Frame 1350 shows a warning that removal requires SELECT+Y+A. An isolated Y press at 1500 leaves that warning on screen through frame 1700. On `define-player-confirm`, SELECT+Y+A at frame 1600 enters the name editor by frame 1900. The warning's cancel variant stays on the warning through frame 1900.
3. On `rename-player`, two Down presses and Start enter RENAME WHO; Start on MIKE opens the character picker by frame 1300. The picker is still displayed at frame 1450. No cartridge RAM name bytes changed in snapshots at frames 700, 950, 1150, 1300 and 1450. Editing and completion remain to be measured.
4. On `define-league`, three Down presses and Start show the six league slots, ONE through SIX, each DEFINE ME. Start on ONE produces a warning by frame 1450. `define-league-confirm` presses SELECT+Y+A at 1650 and shows PICK YOUR LEAGUE by frame 1950; `define-league-cancel` presses Y and remains on the warning. The native LEAGUE tournament itself is outside this task.
5. The four RECORDS categories have distinct screens on their tested cold paths. `track-records` shows tour medals and three empty time slots at frame 1300. `records-high-scores` shows zeroed win/loss/race/stunt averages at 1300. `player-scores` shows MIKE's zeroed summary at 1300. `group-tables` shows the empty DEFINE ME league table at 1300. These are cold-data observations only; they do not establish navigation across tours, populated records, scoring formulas or persistence.
6. On the cold `rename-player` path, the 352 bytes of cartridge RAM `$77:000C-016B` at frame 700 are byte-identical to the pinned ROM bytes from file offset `0x1800C`, the v27 pack's `front-end.rider-names` source. `define-player-confirm` changes MIKE's four non-underscore name bytes at offsets `0x000C-000F` to underscores at frame 1600, plus checksum bytes `0x016C-016D`; it changes no other SRAM bytes through 2050. Its Y-only control changes no SRAM byte. `define-league-confirm` changes the label at `0x016E-0178`, checksum bytes `0x022E-022F` and mode word byte `0x0742` at frame 1651; its Y-only control changes no SRAM byte through 2050. These claims cover a cold MIKE and first league slot only, not populated data or the whole reset behavior.
7. The native unmodified OPTIONS mode stops at the main-menu choice. An `app-debug` baseline build in `.worktrees/options` passed with the pinned isolated toolchain. No native OPTIONS implementation is yet compared.

## Provisional interpretations and decisions

- The static branch table suggests RECORDS enters `$80:D525`, DEFINE PLAYER `$80:C12A`, RENAME PLAYER `$80:D448`, and DEFINE LEAGUE `$80:9BC4`. The new captures execute each of those ranges, but their precise entry/exit and all subroutines need a regenerated dynamic listing before citing their meanings in code.
- Mutable player names need a native owner separate from the pack's immutable default stream. An Astra/medium read-only architecture consultation found direct pack-name consumers in rider selection, NOW PLAYING, local modes, result screens and race HUD, plus a soft-reset path that preserves records alone. Before choosing a schema, measure name entry and reset, and compare the original's mutations and checksums. `front_end_runner --records` currently writes a partial SRAM projection and cannot prove whole-SRAM equality for this task.
- Next experiment: finish one non-default name, reopen its display and soft reset; confirm and cancel a populated player's removal; define a league with varied slots; capture records screens with populated data. Freeze exact state/picture domains before native implementation and preserve all unchanged SRAM ranges as a check.
